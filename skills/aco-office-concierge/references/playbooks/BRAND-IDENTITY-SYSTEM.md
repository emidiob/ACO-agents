# Identity as a tested system, not a moodboard

Original ACO operational method · v0.6.0. Select for the relevant task; do not load every playbook.

## Inputs and independence
Confirm brand scope, approved strategy, required applications and any existing elements that must stay. For an audit, separate extracted observations from endorsed rules. Never declare a downloaded font or image available for commercial redistribution because it was visible on a website.

## Build the system
Connect the concept to type behavior, hierarchy, spacing, color roles, image treatment, graphic elements, motion and voice. A logo is one component. Define principles that work across actual content and formats. Offer contrasting routes only when needed and explain their tradeoffs. Do not reuse a fashionable recipe independent of the brief, or introduce arbitrary bans on colors, typefaces or components.

## Stress test
Apply the direction to representative real content: smallest and largest mark uses, long titles, multiple languages, low-quality imagery, mobile layouts, editorial pages and required print/digital items. Test light/dark and one-color versions only when relevant. Check contrast and reading order with the appropriate evidence, plus manual review. Brand consistency does not justify inaccessible interaction.

## Source and asset control
Track which assets are original, supplied, licensed, generated or placeholders. Request source vectors and font licences where necessary. Describe generation or compositing without calling it a final approved asset. Never distribute font binaries in ACO or a client deliverable without the appropriate licence.

## Guidelines and rollout
Write usable do/don't examples tied to decisions, not dozens of ceremonial pages. Document token roles, component patterns, image credits, motion limits and owners. Mark approved vs experimental rules. Plan rollout for the existing site, files, templates and legacy assets without silently changing the client's identity. Recheck final exports and applications, not only the source design.

## Persistence
One Brand section is canonical. A DESIGN.md in an actual codebase is an implementation contract when needed; link it rather than creating another persistent Drive brand file. Share approved values across web and social without importing another client's defaults. Save an actual identity package only when it is a requested deliverable.
